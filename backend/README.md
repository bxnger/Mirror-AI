# MIRROR AI — backend

> Your future self starts with today's decisions.

MIRROR AI — персональная система, которая строит структурированную цифровую модель пользователя
и замыкает **Decision-to-Outcome Loop**:

```
Understand → Simulate → Decide → Execute → Measure → Adapt
(Current/Future Self) (What If) (выбор) (план) (Reality Check) (Adaptive Memory)
```

**Future Self — это желаемое состояние, а не прогноз.** Система не предсказывает баллы, уровни или
даты достижения и не выдаёт эвристики за статистику.

Эта папка — backend, LLM и база данных. Основной интерфейс — Next.js-фронтенд в корне репозитория.
`backend/web/` — встроенная демо-консоль backend: она нужна, чтобы показать и проверить весь цикл
без фронтенда. Подключение Next.js-фронтенда идёт по `docs/backend-contract.md`.
Все команды ниже выполняются из папки `backend/`.

## Быстрый старт

### Вариант 1 — локально (SQLite, без Docker)

```bash
cd backend
pip install -r requirements.txt
python -m uvicorn app.main:app --port 8000
```

Откройте http://localhost:8000 → **«Запустить DEMO: студент из Казахстана»**.
API-документация: http://localhost:8000/docs.

### Вариант 2 — PostgreSQL через Docker

```bash
cd backend
cp .env.example .env        # при желании впишите ANTHROPIC_API_KEY
docker compose up --build
```

Если порт 8000 занят, задайте другой: `MIRROR_PORT=8080 docker compose up --build`.

### AI-объяснения (Claude)

Добавьте `ANTHROPIC_API_KEY` в `.env`. Без ключа What If Lab работает на детерминированных
шаблонных объяснениях: продукт полностью функционален офлайн, а в интерфейсе видно, какой
генератор использован.

### Тесты

```bash
cd backend
python -m pytest -q
```

Те же тесты на PostgreSQL: `TEST_DATABASE_URL=postgresql+psycopg://mirror:mirror@localhost:5432/mirror_ai python -m pytest -q`.

### CI

`.github/workflows/backend.yml` на каждый push в `backend/` прогоняет тесты и консольное демо на SQLite и на
PostgreSQL 16, а также собирает Docker-образ.

### Демо в консоли

```bash
cd backend
python -m scripts.run_demo
```

## Архитектура

Один backend (FastAPI) и одна база данных (PostgreSQL / SQLite через SQLAlchemy). Демо-консоль `web/` —
статическая страница без сборки, её отдаёт тот же сервер.

```
backend/app/
  models.py            — схема БД: Current Self, Future Self, сценарии, решения, планы, Reality Check, память
  services/
    twin.py            — представление цифрового двойника (Current и Future отдельно)
    gap.py             — Gap Analysis (чистые функции)
    whatif.py          — математика сценариев (чистые функции)
    explain.py         — LLM-объяснение (Claude) + шаблонный fallback + сверка чисел
    loop.py            — Understand / Simulate / Decide
    planner.py         — Execute: недельный план из выбранного сценария
    reality.py         — Measure / Adapt: Reality Check и предложения с подтверждением
    memory.py          — Adaptive Memory: журнал событий + построение контекста
  demo.py              — DEMO DATA и полный демо-сценарий
  main.py              — REST API
backend/web/           — демо-консоль backend (index.html, app.js, style.css)
backend/tests/         — unit + интеграционные тесты всей цепочки
```

### Current Self и Future Self не смешиваются

| Current Self (факты) | Future Self (желаемое) |
|---|---|
| `CurrentProfile`: свободные часы, дни, ограничения | `FutureProfile`: видение, горизонт, желаемые достижения |
| `CurrentState` (на цель): текущее значение/уровень + источник (тест / самооценка) | `FutureTarget` (на цель): целевое значение/уровень, дата, приоритет |
| выполненные `PlanTask`, отмеченные `Milestone` | `Milestone`: промежуточные этапы |

`Goal` — общий якорь, который связывает факт с желаемым состоянием. Пример: `Python — beginner`
хранится в `CurrentState`, `Python — intermediate` — в `FutureTarget`. Адаптация никогда не
меняет Future Self: целевые значения меняются только явным запросом пользователя (`PUT …/target`).

### Gap Analysis

Для каждой цели система показывает:
* **числовой разрыв** (SAT 1180 → 1400 = +220 баллов, 18% шкалы);
* **разрыв по шкале** (CEFR B1 → B2 = 1 уровень, путь `B1 → B2`);
* оставшиеся **промежуточные этапы**;
* **время**: недели до даты и часы, которые *сам пользователь* выделил в выбранном сценарии;
* **допущения** (источник данных, самооценка) и **недостающие данные**.

Система **не считает**, сколько часов «нужно» для прироста баллов — для этого нет валидированной
модели. Это явно записано в допущениях каждой цели.

### What If Lab: числа считает код, LLM объясняет

`whatif.py` программно рассчитывает для каждого сценария: часы и долю на цель, суммарную нагрузку,
загрузку и запас времени, часы до целевой даты, ранжирование, разницу с базовым сценарием и
**индекс соответствия приоритетам** (1 − расстояние полной вариации между долями часов и долями
приоритетов; это эвристика, не вероятность). Риски определяются правилами: превышение времени,
цель без часов, слишком мало часов, концентрация >60%, **расхождение с фактическим темпом из Reality Check**.

`explain.py` передаёт эти расчёты Claude (`claude-opus-5-5`, structured output по JSON-схеме).
Модель объясняет преимущества, компромиссы, риски, недостающие данные и соответствие приоритетам.
Защита:
* системный промпт запрещает прогнозы и выдуманную статистику;
* каждое число в объяснении сверяется с расчётом (`numbers_check`); непроверенные числа подсвечиваются в UI;
* при отказе модели, ошибке сети или невалидном ответе используется шаблонное объяснение.

### AI-разбор недели (Reality Check)

После Reality Check тот же слой (`explain.explain_reality`) объясняет неделю: что сработало, что
мешало, фокус следующей недели и вопросы пользователю. Модель опирается на план/факт, отзыв и историю
из памяти. Менять цели, приоритеты или часы ей запрещено: это делают только предложения адаптации
после подтверждения пользователя.

### Adaptive Memory

Таблица `memory_events` — журнал всех изменений (только добавление записей). Обязательные типы:
`goal_changed`, `skill_changed`, `scenario_chosen`, `plan_generated`, `task_completed`,
`reality_check`, `feedback`, `availability_changed`.
`memory.build_context()` превращает журнал в актуальный контекст: заявленное и **фактическое**
время (окно — последние 4 Reality Check), фактические часы по каждой цели, выбранный сценарий,
отзывы. Этот контекст используют What If (риски), планировщик (адаптация) и LLM.

### Decision-to-Outcome Loop: как этапы связаны в данных

```
Scenario ──(Comparison)──▶ Decision ──▶ Plan ──▶ PlanTask ──▶ RealityCheck ──▶ AdaptationProposal
    ▲                                    │                         │                    │
    └──────────── новая ревизия сценария + новое Decision ◀────────┴──── подтверждение ─┘
```

* План создаётся **только** из выбранного сценария (`409`, если решения нет).
* Следующий план нельзя создать, пока не проведён Reality Check текущего (`409`).
* Reality Check хранит `plan_id`, `scenario_id`, `decision_id`.
* Предложения адаптации (например, «Python 4 → 2.5 ч/нед») **применяются только после подтверждения**.
  После подтверждения создаётся новая ревизия сценария и новое решение. При отказе остаётся решение пользователя.
* Без подтверждения планировщик меняет только тактику: переносит незавершённые задачи и сокращает
  занятия до 45 мин там, где выполнено меньше 80% плана.

## Демонстрация для комиссии (DEMO DATA)

Пользователь: **Айгерим (DEMO)**, студентка из Казахстана, 12 свободных часов в неделю.
Цели: SAT 1180 → 1400, English B1 → B2, Python beginner → elementary.

1. **«Запустить DEMO»** — создаются Current Self и Future Self (шаг 1–2).
2. Блок **Gap Analysis** — шкала SAT, уровни CEFR, этапы (шаг 3).
3. **What If Lab → «Сравнить выбранные»** — сценарий A (SAT 6 / Python 4 / English 2) против B (8 / 2 / 2) (шаг 4).
4. Таблица расчёта + **AI-объяснение компромиссов** (шаг 5).
5. **«Выбрать»** сценарий A с обоснованием (шаг 6).
6. **«Сгенерировать план недели»** — 12 ч по дням, Пн–Сб, этапы по порядку (шаг 7).
7. **«Отметить неделю (DEMO)»** или вручную ✓ / ½ / ✕ (шаг 8). DEMO-результат: Python выполнен на 2.5 ч из 4.
8. **Reality Check** с отзывом → AI-разбор недели и предложение «Python 4 → 2.5 ч/нед» (шаг 9).
9. **«Подтвердить»** → **«Сгенерировать следующий план»** — блок **Adapt** показывает, что изменилось и почему:
   распределение, короткие занятия, перенос задач (шаг 10).
10. **Adaptive Memory** — контекст и журнал всех событий (каждое помечено DEMO).

Дополнительно на защите: **«Обновить факт»** у SAT (например, новый пробный тест 1250). Разрыв
пересчитается до +150, в карточке появится история факта 1180 → 1250, а в памяти — запись `skill_changed`.
«Изменить цель» и «Изменить доступное время» тоже пишутся в память, а цели меняются только по решению пользователя.

Все демонстрационные значения отмечены как **DEMO** в интерфейсе, данных и журнале памяти.

## Recovery Preview (P0)

«План учёбы изменился. Что реально сделать сейчас?» — `POST /api/recovery/preview` детерминированно
пересчитывает неделю под новое время: что оставить, сократить и отложить, резерв и один следующий шаг
(~10 минут). Без пользователя, без базы данных, без LLM: это только предпросмотр, ничего не сохраняется.
Демо (6 ч → 3 ч): `GET /api/recovery/demo`. Контракт: [`docs/recovery-contract.md`](../docs/recovery-contract.md),
логика: `app/services/recovery.py`, тесты: `tests/test_recovery.py`.

## Ограничения MVP

* Схема создаётся через `create_all` при старте, а новые nullable-колонки автоматически добавляются в
  существующую базу (`db._add_missing_nullable_columns`). Для продакшена стоит подключить Alembic-миграции.
* Нет аутентификации: пользователь выбирается по ID (достаточно для демо, не для публичного запуска).
* Сложная аналитика, долгосрочная история и настройки двойника — третий приоритет, в MVP не входят.
